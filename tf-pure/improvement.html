0. Start state & targets

This repo is a pure-Java, keras-flavoured autograd engine (micrograd lineage: tape-based define-by-run). Everything runs on the CPU — no TensorFlow DLL. The fashion-cnn demo (an MLP: Reshape(28,28)→Flatten→Dense(128,relu)→Dense(10)) seemed slow, so the session goal was:

  • Memory: evaluating the whole 10k test set in one forward pass builds a giant autograd tape (1.5 GB+ of intermediates) and risks OOM under -Xmx1g.
  • Speed: one epoch took ~3.8 s after batching alone; ~30% of the epoch is still pure matmul time. Squeeze the GEMM.

1. Batched inference (memory)

Concept

predict pushes every sample through the whole network and keeps the tape and every intermediate tensor alive. With 10,000 rows of 784 floats the intermediate tensors dwarf the heap (>1.5 GB) — the reason evaluation took ~1 minute (thrashing) or died under -Xmx1g. The fix is the standard minibatch loop: run the net on slices of 512 rows, release the tape via Tensor.resetGraph() after each slice, and concatenate the outputs.

Before

src/main/java/puretf/nn/Sequential.java — before (single pass over the whole set)
public float[][] predict(float[][] X) {
    setTraining(false);
    Tensor.resetGraph();
    int n = X.length, d = X[0].length;
    Tensor out = forward(Tensor.of(flatten(X), n, d));   // ALL rows at once
    int cols = out.data.length / n;
    float[][] res = new float[n][cols];
    for (int i = 0; i < n; i++)
        System.arraycopy(out.data, i * cols, res[i], 0, cols);
    return res;
}

public double[] evaluate(float[][] X, int[] Y, int classes) {
    float[][] logits = predict(X);                       // same problem
    ...
}

After

src/main/java/puretf/nn/Sequential.java — after (sliced, tape released per slice)
/** Raw outputs in slices of {@code batch} rows so the autograd tape and
 *  intermediates never balloon to the full dataset size. */
public float[][] predict(float[][] X, int batch) {
    if (batch <= 0) batch = X.length;
    setTraining(false);
    int n = X.length, d = X[0].length;
    int cols = -1;
    float[][] res = new float[n][];
    for (int start = 0; start < n; start += batch) {
        int len = Math.min(batch, n - start);
        Tensor.resetGraph();                  // drop the previous slice's tape
        float[] bx = new float[len * d];
        for (int i = 0; i < len; i++)
            System.arraycopy(X[start + i], 0, bx, i * d, d);
        Tensor out = forward(Tensor.of(bx, len, d));
        if (cols < 0) cols = out.data.length / len;
        for (int i = 0; i < len; i++)
            System.arraycopy(out.data, i * cols, res[start + i] =
                    new float[cols], 0, cols);
    }
    return res;
}

public double[] evaluate(float[][] X, int[] Y, int classes) {
    return evaluate(X, Y, classes, 512);
}
public double[] evaluate(float[][] X, int[] Y, int classes, int batch) {
    float[][] logits = predict(X, batch);    // batched under the hood
    ...
}

Autograd tape: every op records a backprop closure so backward() can walk creation order in reverse. In inference you only need the forward values — keeping the closures alive is pure memory waste, so predict now calls Tensor.resetGraph() between slices.

2. Profile first: where the time actually goes

Concept

Guessing “conv is slow” is how you waste an afternoon. JDK Flight Recorder (JFR) samples the running JVM cheaply. Recording a single epoch told us the demo is a plain MLP (the Reshape→Flatten path, not im2col conv) and that ~89% of the epoch was inside Tensor.matmul: backward ≈ 60% (two matmuls), forward ≈ 28%. One epoch = 118 batches of [512×784]·[784×128] ≈ 18 GFLOP; the scalar dot-product loops were holding ≈10 GFLOPS.

start JFR at ~10s, stop automatically at 60s (or run one epoch)
java -XX:StartFlightRecording=duration=60s,filename=bench.jfr ^
     -XX:StartFlightRecording=dumponexit=true,settings=profile -jar ...
jfr print --events jdk.ExecutionSample bench.jfr > samples.txt

Lesson: don’t optimize what you haven’t measured. The interesting number was which matmul: the backward dW = AᵘG and dA = G·Wᵘ together beat the forward. Optimize all three kernels.

3. Vectorize matmul with the JDK Vector API

Concept — SIMD and the incubator module

  • SIMD: one CPU instruction operates on several floats at once. On AVX2 a “vector” holds 8 floats (256 bit); on AVX-512, 16.
  • Species: FloatVector.SPECIES_PREFERRED is the largest width the JVM picked for this CPU (8 on your machine — you must use its lane count as the unit of work).
  • Primitives: fromArray(SP, arr, off) loads lanes, intoArray stores them, broadcast repeats one scalar, mul/add are lanewise, reduceLanes(ADD) sums a vector to a scalar.
  • Incubator module: the API lives in jdk.incubator.vector (not java.lang.vector) even on JDK 23 — so both the compiler job and the run JVM need --add-modules jdk.incubator.vector. FloatVector.SPECIES_PREFERRED.length() is 8 here, so a 128-wide row is exactly 16 vectors.
  • Dissection: the kernel keeps the k loop outer so each row of W is streamed sequentially (full cache lines), the j loop runs 8 lanes at a time, and the zero-skip before the j loop is a real win for pixel/ReLU inputs that are ⋅half⋅ zeros.

Before — scalar loops

src/main/java/puretf/Tensor.java — matmul before (three scalar triple-loops)
public Tensor matmul(Tensor w) {
    int b = shape[0], m = shape[1], n = w.shape[1];
    float[] out = new float[b * n];
    ...
    // forward: for each row i, for each k, scatter a[i,k] * W[k,:]
    for (int i = 0; i < b; i++)
        for (int k = 0; k < m; k++) {
            float a = data[i * m + k];
            if (a == 0f) continue;
            int oo = i * n;
            for (int j = 0; j < n; j++)
                out[oo + j] += a * w.data[k * n + j];
        }
    ...
    // backward dA: for each (i,k) a full length-n dot product
    for (int i = 0; i < b; i++)
        for (int k = 0; k < m; k++) {
            float s = 0;
            for (int j = 0; j < n; j++)
                s += r.grad[i * n + j] * w.data[k * n + j];
            da[i * m + k] = s;
        }
    // backward dW: for each (k,i) outer-product accumulation
    for (int k = 0; k < m; k++)
        for (int i = 0; i < b; i++) {
            float a = data[i * m + k];
            if (a == 0f) continue;
            for (int j = 0; j < n; j++)
                dw[k * n + j] += a * r.grad[i * n + j];
        }
}

After — Vector API

The same three kernels moved into dedicated private methods invoked from matmul; each has a scalar fallback for when n is smaller than one lane group.

src/main/java/puretf/Tensor.java — after (vectorised)
private static final VectorSpecies<Float> SP = FloatVector.SPECIES_PREFERRED;

/** Forward rows [i0,i1) x W[m,n] -> out rows. k stays outer so each W row
 *  streams sequentially; one broadcast avoids 8x redundant broadcast. */
private static void mmFwd(float[] out, float[] a, float[] wd,
                          int i0, int i1, int m, int n) {
    if (n < SP.length()) {                     // scalar fallback
        for (int i = i0; i < i1; i++)
            for (int k = 0; k < m; k++) {
                float av = a[i * m + k];
                if (av == 0f) continue;
                int wo = k * n, oo = i * n;
                for (int j = 0; j < n; j++)
                    out[oo + j] += av * wd[wo + j];
            }
        return;
    }
    for (int i = i0; i < i1; i++) {
        int oo = i * n, ai = i * m;
        for (int k = 0; k < m; k++) {
            float av = a[ai + k];
            if (av == 0f) continue;            // skip whole k for sparse layers
            FloatVector bv = FloatVector.broadcast(SP, av);
            int wo = k * n, j = 0;
            for (; j + SP.length() <= n; j += SP.length()) {
                FloatVector o  = FloatVector.fromArray(SP, out, oo + j);
                FloatVector wv = FloatVector.fromArray(SP, wd, wo + j);
                o = o.add(wv.mul(bv));         // out[j..] += a * W[k,j..]
                o.intoArray(out, oo + j);
            }
            for (; j < n; j++) out[oo + j] += av * wd[wo + j];  // tail lanes
        }
    }
}

/** dA[i0..i1,:] = G . W^T - one vectorised dot product per (i,k). */
private static void mmBwdDa(float[] da, float[] g, float[] wd,
                            int i0, int i1, int m, int n) {
    if (n < SP.length()) { /* scalar, same as before */ return; }
    for (int i = i0; i < i1; i++) {
        int go = i * n, oi = i * m;
        for (int k = 0; k < m; k++) {
            int wo = k * n, j = 0;
            FloatVector accv = FloatVector.zero(SP);
            for (; j + SP.length() <= n; j += SP.length())
                accv = accv.add(FloatVector.fromArray(SP, g, go + j)
                        .mul(FloatVector.fromArray(SP, wd, wo + j)));
            float s = accv.reduceLanes(VectorOperators.ADD);   // dot -> scalar
            for (; j < n; j++) s += g[go + j] * wd[wo + j];
            da[oi + k] = s;
        }
    }
}

/** dW[k0..k1,:] += A^T . G (accumulates over the whole batch). */
private static void mmBwdDw(float[] dw, float[] g, float[] a,
                            int k0, int k1, int b, int m, int n) {
    if (n < SP.length()) { /* scalar, same as before */ return; }
    for (int k = k0; k < k1; k++) {
        int wo = k * n;
        for (int i = 0; i < b; i++) {
            float av = a[i * m + k];
            if (av == 0f) continue;
            FloatVector bv = FloatVector.broadcast(SP, av);
            int go = i * n, j = 0;
            for (; j + SP.length() <= n; j += SP.length()) {
                FloatVector d  = FloatVector.fromArray(SP, dw, wo + j);
                FloatVector gv = FloatVector.fromArray(SP, g, go + j);
                d = d.add(gv.mul(bv));         // dw[k,j..] += a[i,k] * g[i,j..]
                d.intoArray(dw, wo + j);
            }
            for (; j < n; j++) dw[wo + j] += av * g[go + j];
        }
    }
}

Why 3.8 s→2.5 s: Warm (JDK 23) epoch timings after the compile flags below — loss stayed bit-identical (0.6536, acc 0.7793). The inner loop now does 8 output elements per vfmadd instead of one scalar multiply/add, with the load of W[k,:] kept sequential so the prefetcher can stream full cache lines.

Gotcha caught on the way — fma operand order

While tuning tiling I tried acc.fma(wv, broadcast(x)) and the epoch loss instantly went from 0.6536 to 2.28 (train corrupted). A two-line probe revealed the truth about this JDK’s incubator API:

// probe:  a=2  v1=3  v2=4
FloatVector f = va.fma(vb, vc).lane(0);   // = 10  (<-- 2*3+4, NOT 2+3*4)
FloatVector m = va.add(vb.mul(vc)).lane(0);// = 14

Vector.fma(v1,v2) computes this * v1 + v2 on this JDK, not this + v1*v2. The correct fused form for an accumulator is acc = wv.fma(broadcast(x), acc), or simply keep acc.add(wv.mul(bv)). Always verify kernel numerics against a scalar reference before benchmarking.

4. Config needed to run

Concept

The incubator module must be visible in both phases: javac needs it, and the run JVM needs it. exec:java spawns the app inside Maven’s own JVM, so JVM flags belong in MAVEN_OPTS, not in exec-maven-plugin <arguments> (those are program args passed to main() — putting --add-modules there made the demo treat it as a data directory: NoSuchFileException: jdk.incubator.vector\train-images-idx3-ubyte.gz).

pom.xml — compile at Java 21 + expose the module to javac
<properties>
  <maven.compiler.release>21</maven.compiler.release>
  <exec.mainClass>puretf.demo.CnnFashionMnistDemo</exec.mainClass>
</properties>
<build><plugins>
  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.13.0</version>
    <configuration>
      <release>21</release>
      <compilerArgs>
        <arg>--add-modules</arg>
        <arg>jdk.incubator.vector</arg>
      </compilerArgs>
    </configuration>
  </plugin>
  <!-- exec-maven-plugin: keep ONLY <mainClass>. No <arguments> block. -->
</plugins></build>

  • If you ever see java.nio.file.NoSuchFileException: jdk.incubator.vector\..., a --add-modules ... pair leaked into main() args — move it to MAVEN_OPTS.

5. The tiled-GEMM detour (measured, not merged)

Concept

With the vector loop bound by memory, the “textbook” next step is register tiling — hold part of the output row in registers across several k steps and write it once, avoiding a load+store round-trip per k. That needs k-outer→j-inner layouts, a curry or row-blocked micro-kernel, and fewer than ~16 live vectors (YMM registers).

What was tried (variants)

KernelOrderLive vectorsEpochVerdict
k-blocked, js-outer column scanjs→k→j~17 (spills)5.7 sstrided W loads waste half of every cache line
row-blocked RB=8 (unrolled 8 accs)i-block→js→k17 > 16 regs3.2 sregister spills
row-blocked RB=4 + fmai-block→js→k~82.9–3.3 sfma operand bug corrupted loss; fixed logically
half-row register swap, full k insidei→tile→k~92.7 ssequential W, but re-reads W per tile + long FMA chains
simple k-sequential vector loopi→k→j~32.5 swinner — kept

Conclusion: for this workload (n=128, W = 400 KB comfortably L2-resident, already-buffered output rows) the extra W re-reads and long per-accumulator FMA dependency chains outweigh the saved output round-trips. The simple streaming loop wins; the tiled experiments were removed. The lesson stands: measure variants, keep the fastest.

6. Improving training via batch size & other knobs

Batch size (--batch=N, default 512)

  • Throughput: larger batches issue bigger GEMMs, so FLOPs per second goes up — until the intermediate tensors stop fitting in L2/L3. Here 512 is sweet; 1024 is usually also fine for this MLP, and evaluation can use a bigger batch than training with no accuracy effect.
  • Memory: the tape holds one whole batch of intermediates, so heap scales linearly with batch — keep it ≤~1024 under -Xmx1g. The 10k test set is always sliced to --batch regardless.
  • Gradient quality: bigger batch = lower-variance gradient estimate per update but fewer updates per epoch. For a small model start 256–512; if accuracy plateaus early, try smaller (64–128) or raise LR proportionally (linear scaling rule: ×2 batch ≈ ×2 max LR).
